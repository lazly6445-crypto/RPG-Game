## 3. 측정 환경

### 3.1 기준 기기 **[확정: 결정 95·96·102]**
| 항목 | 값 |
|---|---|
| 목표 | 통합 그래픽 또는 엔트리 GPU, RAM 8GB (결정 3) |
| 실제 기종 | **사용자의 현재 PC(CPU-Z 스크린샷 기준, 결정 96):** Intel Core i5-12400F(6C/12T) · DDR4 32GB(듀얼 채널) · NVIDIA GeForce RTX 3060 Ti(VRAM 8GB) · Gigabyte B660M DS3H DDR4. **저장장치는 SSD(NVMe/SATA 미확인), OS는 Windows(결정 102)** |
| 기준 대비 | 목표 최저 사양보다 **훨씬 강하다.** 12400F는 내장 그래픽이 없는 모델이라 통합 그래픽을 이 PC에서 **직접 재현할 수 없다** |
| 근사 방법 **[제안, 결정 96]** | ① 출력 해상도 720p·품질 최저로도 측정 ② **CPU 프레임 비용과 GPU 프레임 비용을 분리해 기록**(cpu_ms, gpu_ms) ③ 메모리를 8GB로 제한한 상태에서도 한 번 측정(운영체제 기능으로 제한 가능한지 **미확인**, P0 1주차 확인) ④ **안전 마진:** 이 PC에서 평균 프레임타임이 합격선의 **50% 이하**여야 저사양 합격으로 본다 **[가정, 근거 없음]** ⑤ 통합 그래픽 실제 성능은 알 수 없으므로 GPU 의존 항목(오버드로, 큰 스프라이트·셰이더, 메모리 대역폭)은 보수적으로 설계하고 출시 전 베타에서 보완한다. 2D 픽셀은 GPU 부담이 작다고 **추정**하지만 확인한 것은 아니다 |
| 실제 기기 | **구하지 않는다(결정 95).** 근사 측정만 하고 근사했음을 기록한다 |

기기 정보는 CPU, GPU, VRAM(공유 메모리 포함), RAM, 저장장치 종류, OS, 드라이버 버전, 출력 해상도, 엔진 버전을 매 측정 파일의 머리말에 기록한다.

### 3.2 공통 조건
- 내부 렌더 해상도 **640×360**(결정 113), 출력 1920×1080(3배 정수 확대) 기본, 1280×720(2배) 병기 **[가정]**.
- 타일 **32px**(결정 112), 스프라이트 8방향(결정 114).
- 수직 동기화 끔(프레임타임 측정용), 별도로 켠 상태의 체감 확인.
- 빌드: 에디터 실행이 아니라 **릴리스 유사 빌드**로 측정(에디터 성능은 참고용으로만 기록).
- 측정 전 워밍업 60초, 측정 구간 5분 이상, 동일 경로를 3회 반복 **[가정]**.
- 백그라운드 프로그램 종료, 전원 계획 고성능.

## 4. 측정 항목

### 4.1 타일 월드 스트리밍 테스트 (G1)
| 항목 | 내용 |
|---|---|
| 테스트 월드 | **1024×1024 타일**(32px, 약 32,768×32,768 픽셀) **[가정, 결정 79 "중간 크기"의 상한 확인용]**. 지형은 4종 지역 땅빛 더미 + 건물·식생 더미 타일/오브젝트, 높이 값 배열 포함 |
| 청크 | 청크 크기 예: 32×32 타일 **[가정, 측정]**. 플레이어 주변 N청크만 로드/언로드 |
| 경로 | 월드를 가로지르는 고정 경로(왕복, 8방향 이동), 최고 이동 속도로 한 번 더 |
| 측정 | 평균/99퍼센타일 프레임타임, 100ms 초과 히치 횟수, 메모리, 로드된 청크 수, 로딩 지연(맨눈 팝인 포함 기록), 디스크 사용량 |
| 합격선 | 평균 33ms 이하, 99퍼센타일 50ms 이하, 10분 이동에 100ms 초과 히치 0회 |
| 비고 | 엔진에 타일 청크 스트리밍 기본 기능이 없으면 **직접 만든 단순 청크 로딩**을 사용하고 구현 시간을 기록한다. Godot는 월드를 여러 레이어로 나눠 플레이어 위치에 따라 로드하라는 2차 권고가 있다(미검증) |

### 4.2 지형 변형 최소 시나리오 (G2)
결정 115(빌더즈식 블록 높이)·98(최대 한계)·99(기초 보호)·71(지도 미반영)의 구현 가능성과 비용을 본다. 상세 규칙은 `2d-transition-impact.md` §4.2.
| ID | 시나리오 | 측정 | 합격선 **[가정]** |
|---|---|---|---|
| T1 | **쌓기/깎기:** 지점을 겨눠 높이 +1/−1. 인접 타일에 **절벽 타일 오토타일 갱신** | 입력 → 화면 반영 지연(`edit_latency_ms`), 연속 편집 중 프레임타임 | 지연 평균 100ms 이하, 변형 중 평균 33ms/99퍼센타일 50ms 이하 |
| T2 | **이동 규칙:** 높이 차 1은 오르고 2 이상은 막힘. 변형 직후 충돌 갱신 | 변형 직후 3프레임 안에 규칙대로 동작 | 오동작 0/50회 |
| T3 | **다리·계단 만들기:** 높이 차 2 이상 구덩이를 쌓아 건넘(미오 2단계 상당) | 쌓은 타일 위를 8방향으로 이동 | 끼임·튕김 0/20회 |
| T4 | **델타 저장·불러오기:** 변경 타일 1000곳 **[가정]** (좌표, 높이 값) 저장 → 새 프로세스에서 불러오기 | 저장 용량·시간, 복원 일치(타일 해시) | 저장 1초 이하, 불러오기 3초 이하(SSD), 복원 100% 일치, 용량 **[측정]**(임시 1MB 이하) |
| T5 | **청크 경계 편집:** 경계에 걸친 편집, 청크 언로드/재로드 후 델타 복원 | 시각 이상(틈·절벽 불일치), 델타 유실 | 20회 반복 이상 0건 |
| T6 | **마소 농도 3단계 한계:** 옅음/중간/짙음 구역에서 같은 입력의 최대 높이·깊이 | 한계가 규칙대로 적용되는가 | 규칙 일치 100%(임시 한계는 결정 115 예시 +1/−1, +3/−2, +4/−3 [가정]) |
| T7 | **건축물 기초 보호:** 건축물 바닥 면 + 여유 1칸을 변형 불가로 표시·차단 | 마스크 처리 정확도 | 침범 0/50회 |
| T8 | **구덩이 함정(대형 더미):** 더미 대형이 정해진 경로로 걷고 구덩이 타일에 진입하면 빠진다(무방비 8초 **[가정]**) | 판정 오류, 경로 갱신 비용 | 오판정 1/20회 이하 |

이 시나리오가 불합격인 엔진은 **지형 변형 방식을 타일 상태 전환(A: 평지 ↔ 구덩이 ↔ 돋운 땅 몇 단계)으로 바꿔 한 번 더** 시도한다(공통 퇴로).

### 4.3 이터레이션 속도 (G3)
| 측정 | 방법 | 합격선 |
|---|---|---|
| 코드 수정 → 실행 | 값 하나(이동 속도)를 바꾸고 실행까지 걸린 시간 | 30초 이내 |
| 빈 프로젝트 → 릴리스 유사 빌드 | 빌드 시간 | 10분 이내 |
| 하루 내 수정 사이클 | "전투/이동 값 수정 → 5명 테스트 가능한 빌드" 한 사이클 | 하루(파트타임 3~4시간) 안에 가능 |

### 4.4 도구·오토타일 (G4)
| 측정 | 방법 | 합격선 |
|---|---|---|
| 타일맵 편집 → 플레이 | 지형 구역을 수정하고 플레이로 확인 | 10분 이내 |
| 소품·건물 배치 → 플레이 | 타일 오브젝트·소품 배치 후 확인 | 10분 이내 |
| **절벽 오토타일 규칙 구축** | 높이 차 경계에 절벽 타일을 자동 선택하는 규칙(방향·모서리 조합)을 엔진 도구로 만들어 동작시키는 데 걸린 시간·막힘 | 하루 이내에 최소 규칙 동작 **[가정]**. 구현 방식(엔진 오토타일 vs 직접 스크립트)과 소요 시간 기록 |
| 규칙 기반 산포 | 반복 배치를 스크립트로 자동화 가능한지 | 가능 여부·소요 시간 기록 |

### 4.5 픽셀 퍼펙트 렌더링 (G5)
| 측정 | 방법 | 합격선 |
|---|---|---|
| 정수 배 확대 | 640×360을 1920×1080(3배)·1280×720(2배)로 출력, 흐림·비율 깨짐·여백 확인 | 흐림 없음, 비율 유지 |
| 서브픽셀 이동 | 8방향 이동·카메라 스크롤 중 스프라이트·타일 떨림/찢김 | 눈에 띄는 떨림 없음 |
| 설정 소요 | 엔진별 설정 시간·막힘 | 반나절 이내 **[가정]** |
엔진별 알려진 설정(2차 자료, 미검증): Godot는 스트레치 모드 `viewport` + 정수 스케일 + `nearest` 필터 + 2D 픽셀 스냅, Unity는 URP **Pixel Perfect Camera**(기준 해상도·Asset Pixels Per Unit·픽셀 스냅·업스케일 렌더 텍스처; 공식 문서).

### 4.5a 보조 항목 (평가에 가산, 합격선 없음)
- 스프라이트 8방향 애니메이션 파이프라인: 스프라이트시트 임포트, 애니메이션 편집, 방향 전환 구성 편의, 4방향+미러 지원 여부.
- 학습 곡선: 처음 2주 동안 막힌 횟수와 해결 시간(구현 일지).
- 문서·커뮤니티 자료 충분성.
- 데이터 파일 로딩(규칙표·대사) 편의성, 현지화 지원 방식.

### 4.6 배포 경로 (G7)
- 릴리스 유사 빌드가 **Steam 배포 전제(Steamworks 연동)** 와 호환되는가: Godot는 GodotSteam(공식 튜토리얼: 전용 내보내기 템플릿, godotsteam.dll·steam_api64.dll 동봉, MinGW 금지), Unity·GameMaker는 이번 조사 없음 → 게이트에서 확인. 빈 프로젝트로 연동 최소 테스트(앱 초기화·오버레이 수준)를 한 번 한다.
- Windows 빌드가 깨끗한 환경(개발 도구 없는 PC)에서 실행되는가.
- 빌드 용량: 빈 프로젝트와 월드 테스트 빌드 크기 기록.

## 5. 합격 판정과 선택 규칙

### 5.1 필수 항목 (하나라도 실패하면 불합격)
- 4.1 타일 월드 스트리밍: 평균 33ms 이하, 100ms 초과 히치 10분에 0회
- 4.2 지형 변형: T1(지연·프레임타임), T2, T4, T5, T7
- 4.3 수정 → 실행 30초 이내, 하루 내 수정 사이클 가능
- 4.4 타일맵 편집 → 플레이 10분 이내, 절벽 오토타일 최소 규칙이 하루 이내 동작
- 4.5 픽셀 퍼펙트: 흐림 없음·떨림 없음
- G6 라이선스: 결정 11·93·94·26과 충돌하지 않음

### 5.2 가산 항목 (필수 통과 후 점수 비교, 가중치는 결정 101 유지) **[제안]**
| 항목 | 가중치 |
|---|---|
| 지형 변형 재미(체감, 테스터 3명 중 2명이 의도하지 않은 사용 시도) | 3 |
| 구현 시간(T1~T8 구현 소요) 짧음 | 3 |
| 던전(지하 별도 맵·층 전환)·건축 타일 규칙을 같은 도구로 다루기 쉬움 | 2 |
| 메모리·디스크 여유 | 2 |
| 학습 곡선·자료·애니메이션 파이프라인 편의 | 2 |
| 데이터 중심 설계 편의 | 1 |
| 배포 경로 | 1 |
각 항목 0~2점으로 채점해 가중합을 계산한다. 채점 근거는 측정 로그와 구현 일지에 남긴다. (항목 이름은 2D 전환으로 바뀌었고 가중치 구조는 결정 101 그대로.)

### 5.3 선택 절차
1. 엔진 1(Godot 4) 필수 통과 → 엔진 2(Unity)를 **같은 최소 시나리오로** 측정해 비교한다. 엔진 1 불합격이고 엔진 2 합격이면 엔진 2를 선택한다.
2. 두 엔진이 모두 필수 통과면 가산 점수 높은 쪽. 동점이면 **결정 11·93·94에 덜 민감한 쪽(무료·오픈소스, 즉 Godot)** 을 택한다.
3. 두 엔진이 모두 불합격이면 §7의 퇴로로 한 번 재측정한다.

## 7. 퇴로 **[제안]**

1. **지형 변형 방식 퇴로:** 불합격 시 **타일 상태 전환(A)** 으로 재시험(`2d-transition-impact.md` §4.2). 그래도 불합격이면 변형 범위를 지정 구역(미오 길, 대형 전투방 등)으로 축소.
2. **월드 스트리밍 퇴로:** 직접 구현 단순 청크 로딩도 불합격이면 월드를 **연결된 소규모 맵 여러 개**로 바꾼다. 결정 79(월드 크기 중간)·기둥 2와 연결되므로 월드 구성 재검토가 필요하다.
3. **엔진 퇴로:** 엔진 2도 불합격이면 GameMaker를 같은 방식으로 측정한다. 상업용 유료 일회성 구매이므로 **사용자 결정**(결정 94).
4. **전부 불합격:** 독자 요소(지형 변형) 재검토 → 건축 시스템 중심으로 축소. 사용자 결정 필요.
