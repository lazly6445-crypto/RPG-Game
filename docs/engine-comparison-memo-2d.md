# 엔진 비교 메모 — 2D 픽셀 탑다운 기준 (개정판)

> 이전 메모(`engine-comparison-memo.md`)는 3D 지형 변형(Voxel Tools)을 전제로 했고 결정 108(2D 픽셀 탑다운 전환)로 무효가 됐다. 이 메모가 대체한다.
> 작성 근거: 2026-11-01 웹 검색(대부분 2차 자료). 확인 수준: **A** 공식 문서/약관 원문(요약 포함) · **B** 신뢰할 만한 2차 자료 · **C** 포럼·마켓·벤더 홍보 · **미확인**.
> 이 메모의 순위와 의견은 **제안**이며 최종 엔진은 P0 엔진 게이트(`engine-gate-plan.md`, 개정 필요)에서 실측으로 확정한다.

## 3. 엔진별 확인 사실

### 3.1 라이선스·비용 (R6, R8)
| | Godot 4 | Unity | GameMaker |
|---|---|---|---|
| 개인·소규모 | **MIT, 로열티 없음** (B: GitHub 미러 README, openSUSE 위키. **공식 LICENSE 원문 재확인**) | Personal: 최근 12개월 수익·모금액 **20만 달러 미만**이면 해당 (B 요약, 일부 페이지에 이전 기준 10만 달러 문구가 남아 있어 **약관 원문 확인**) | **비상업은 무료. 상업용(PC·Mac·모바일 판매)은 Professional 일회성 $99.99**(공식 페이지 요약, 지역별 가격 상이). 서드파티 리스팅이 월 구독으로 표기한 것은 공식과 충돌해 신뢰하지 않음(B/C) |
| 콘솔 | 해당 없음(결정 2: PC만) | — | 콘솔은 Enterprise 구독(해당 없음) |
| 이 프로젝트 | 비용 0 | 수익 보너스(결정 26)이므로 한도 미만 가능성이 높음 | **유료 구매 필요 → 결정 94에 따라 사용자 결정** |

### 3.2 타일맵과 런타임 편집 (R1, R2, R3)
| | Godot 4 | Unity |
|---|---|---|
| 타일 시스템 | TileMapLayer(Godot 4.x). 커스텀 데이터 레이어로 타일에 값을 붙일 수 있다는 것은 **일반 지식이며 이번 검색에서 공식 확인하지 못함** | Tilemap(2D). 타일 값은 별도 데이터 구조가 필요할 가능성 높음(**미확인**) |
| 런타임 편집 | `set_cell` 단건 호출 비용 보고: 4.5, 700×700 레이어에서 호출당 약 4~5ms(포럼 C). 각 호출이 내부 갱신을 일으킨다는 추정. **일괄 변경 API 사용·청크별 레이어 분할** 권고(2차 C) | `SetTiles` 일괄 처리 권고(2차). 대량 설정이 매우 느렸다는 구버전 보고(2018, C). 큰 영역 선택 시 FPS 저하가 이슈로 등록(Unity 이슈 트래커, B). 타일맵 레이어마다 드로 콜·메모리 증가 |
| 이 게임에 의미 | 우리 편집은 한 번에 소수의 타일(쌓기/깎기 범위)이라 일괄 처리가 작을 수 있으나, **변형 직후 지형 충돌 갱신까지** 합친 비용은 **미측정** | 동일하게 **미측정** |
| 높이 표현 | 타일별 높이를 화면 위치 오프셋으로 그리는 엔진 패치를 쓴 사용자 사례(포럼 C, 엔진 수정이 필요해 일반 해법 아님). 우리는 높이를 **자체 데이터 배열**로 두고 절벽을 오토타일로 그리는 방식이라 이 패치는 불필요 | 동일 |
| 청크 | 월드를 여러 레이어로 나눠 플레이어 위치에 따라 로드하라는 권고(2차 C) | 내부적으로 타일 청킹이 있으나 크기 튜닝의 공식 문서는 찾지 못함(**미확인**) |

→ **높이 값·변형·델타 저장·이동 규칙은 코드로 직접 구현**하는 부분이라 엔진 선택이 크게 좌우하지 않는다. 엔진의 타일맵 성능과 개발 편의가 차이를 만든다.

### 3.3 픽셀 렌더링 (R4, R5)
| | Godot 4 | Unity |
|---|---|---|
| 방법 | 포럼 권고: 스트레치 모드 `viewport`, 스케일 모드 `integer`, 기본 텍스처 필터 `nearest`, 2D 픽셀 스냅 활성화. 4.5에서 정수 스케일 동작 확인(포럼 C). 구버전은 정수 스케일을 강제 못 했다는 노트가 있어 **버전 확인 필요**. 기본 해상도 320×180과 640×360은 정수 배라 깔끔히 확대된다는 추정은 제 것이며 공식 확인 아님 | URP **Pixel Perfect Camera 컴포넌트**(2D URP 템플릿에 기본 포함). 기준 해상도, Assets Pixels Per Unit, 픽셀 스냅, 업스케일 렌더 텍스처 옵션(공식 문서 A). 버전별 옵션 이름이 다름 |
| 640×360 | 위 설정으로 가능(추정) | 기준 해상도 640×360으로 설정 가능(공식 문서의 예시는 320×180) |

### 3.4 월드·성능 사례
- **코어 키퍼는 Unity + DOTS**(ECS, Jobs, Burst)로 만들어졌다(Wikipedia, 모딩 위키, B). 즉 2D 탑다운 땅 파기·건축 생존 RPG를 Unity로 만든 사례가 있다. 단 코어 키퍼는 DOTS(전문적인 엔진 사용)를 썼고 1인 파트타임 프로젝트와는 규모·숙련도가 다르다.
- Godot 대형 월드 2D 사례, 두 엔진의 정확한 최저 사양 성능: **이번 검색에서 확인하지 못함**.

### 3.5 Steam 배포 (R8)
| | Godot 4 | Unity | GameMaker |
|---|---|---|---|
| Steam | **GodotSteam** 별도 확장. 공식 튜토리얼: 전용 내보내기 템플릿 사용(안 쓰면 실행 파일이 크래시), godotsteam.dll과 steam_api64.dll 동봉, MinGW로 컴파일하지 말 것, SteamCMD/SteamPipeGUI로 업로드(B, 공식 튜토리얼 요약). 가짜 포크 주의 | Steamworks 연동 방법 **이번 조사 없음** | **이번 조사 없음** |
| 비고 | Steam 연동에 설정 단계가 있음. 게이트에서 빈 프로젝트로 한 번 연동 테스트(업적/오버레이 수준) 권장 | — | — |

**1순위 이유(제안):** 무료·MIT, 2D 전용 렌더 경로가 단순, 코드로 직접 만드는 부분이 많은 이 프로젝트에 가볍다. **Unity는** 코어 키퍼 선례와 자료·튜토리얼이 풍부하고 Pixel Perfect Camera가 공식 컴포넌트라는 강점이 있어 근소하게 2순위. 엔진 숙련도가 둘 다 없으므로 **같은 최소 시나리오 실측**이 가장 큰 근거가 되어야 한다.
