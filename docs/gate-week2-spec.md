# 엔진 게이트 2주차 사양 — Godot 4.7.2 타일 월드·지형 변형 측정

> 대상: `engine-gate-plan.md`의 엔진 1(Godot) 측정 중 §4.1(타일 월드 스트리밍), §4.2(T1~T8), §4.3(이터레이션), §4.4(오토타일), §4.5(픽셀 퍼펙트). 선행: `gate-week1-guide.md` 1주차(설치, 640×360 템플릿, Git 저장소; 결과 §11).
> 규칙의 출처: 결정 115(빌더즈식 블록 높이), 116(흙 블록), 117(낙하), 118(범위), 98(최대 한계), 99(기초 보호), 71(지도 미반영), 74(대형 함정), 111~114(탑다운·32px·640×360·8방향). 상세 사양은 `prototype-d-spec.md`.
> 표기: **[확정]** 사용자 결정 · **[제안]** 제안 · **[가정]** 임시값 · **[측정]** 이 주차에 측정해 확정할 값 · **[미결정]** 사용자 결정 필요 · **[확인]** 4.7.2에서 직접 확인할 API/동작.

## 0. 이 주차의 목표와 한계

**목표:** Godot 4.7.2에서 (1) 1024×1024 타일 월드를 청크 단위로 스트리밍하며 640×360 픽셀 퍼펙트로 스크롤하고, (2) 타일 높이 값 변형(쌓기/깎기, 절벽 표시, 이동 규칙, 델타 저장)을 구현해 게이트 합격선(`engine-gate-plan.md` §4~§5)과 비교할 수 있는 측정치를 만든다.
**상한:** 엔진당 2주(결정 100) — 1주차(설치·템플릿) + 2주차(이 문서) 합쳐 Godot에 쓸 수 있는 시간이다. 초과하면 그 시점의 측정으로 판정한다.
**자동화와 사람의 몫:**
- PC 쪽 Claude Code 세션은 **파일 작성, 문법 검사, 헤드리스 논리 테스트(렌더 없음), 로그 파일 분석**을 맡길 수 있다.
- **프레임타임·입력 지연·시각 가독성(흐림, 떨림, 절벽이 높이로 읽히는가)** 은 렌더링이 필요하므로 **사용자가 창 모드로 실행해 CSV와 스크린샷을 만든다.** 헤드리스 로그의 프레임 시간은 GPU 비용을 담지 못하므로 판정에 쓰지 않는다.
- 사용자가 에디터를 열어 두면 파일 충돌 위험이 있다. 파일 수정 작업 중에는 에디터를 닫는다.

## 1. 구현 설계 (제안)

### 1.1 데이터 구조
| 데이터 | 형태 | 비고 |
|---|---|---|
| 월드 크기 | 1024×1024 타일(32px) **[가정]** | 결정 79 "중간"의 상한 확인용 |
| 원본 높이 | 결정론적 생성(`FastNoiseLite` 또는 시드 기반 해시) → 0~3 정수 | 파일로 저장하지 않고 시드로 재생성. 읽기 전용 |
| 변형량 Δh | **희소 저장**: 변경된 타일만 `Dictionary[Vector2i, int]`(좌표→Δh) 또는 청크별 딕셔너리 | 델타 저장 대상(결정 71 분리) |
| 지역 구분(마소 농도) | 월드를 4영역으로 나눔: 옅음(시가지)/중간(경계지)/짙음(요정숲) + 던전 방(짙음) 더미. 저해상도 농도 맵 | 한계표(§1.3) |
| 청크 | 32×32 타일 **[가정, 측정]** | 청크 키 = 타일 좌표 ÷ 32 |
| 흙 블록 보유 수 | 정수 1개 | 결정 116 |

### 1.2 스트리밍 구조 (Godot 타일맵 성능 고려)
- **청크마다 `TileMapLayer` 노드를 따로 둔다**(바닥 레이어 + 절벽 레이어 = 청크당 2개). 큰 단일 레이어에서 `set_cell` 단건 호출이 느렸다는 2차 보고와 "월드를 여러 레이어로 나눠 로드하라"는 권고가 근거다(포럼, 미검증). 단일 레이어 대안은 비교용 보조 측정으로만 한다.
- **로드 반경:** 플레이어 청크 기준 반경 2청크(5×5 = 25청크, 25,600 타일) **[가정, 측정]**. 화면은 약 20×11타일이므로 반경 1(3×3)로도 충분할 수 있다. 반경 1과 2를 비교한다.
- **로드/언로드 비용 분산:** 한 프레임에 로드할 타일 수를 제한(예: 프레임당 청크 1개 또는 1,024타일) **[측정]**.
- 오브젝트(건물 더미)는 이 주차 범위에서 단순 사각형으로 두고 청크에 소속시킨다.

### 1.3 마소 농도별 한계표 (결정 115 예시값) **[가정, 측정]**
| 농도 | 구역 | 쌓기 한계(+Δh) | 깎기 한계(−Δh) | 변형 범위 상한(결정 118) |
|---|---|---|---|---|
| 옅음 | 시가지 | +1 | −1 | 1타일 |
| 중간 | 경계지 | +3 | −2 | 십자 |
| 짙음 | 요정숲·던전 방 | +4 | −3 | 3×3 |
미오 보상(범위 한 단계 확장)은 이 주차에서 **플래그 하나**(`range_bonus`)로 시뮬레이션만 한다.

### 1.4 절벽 표시 (탑다운 3/4 뷰) **[제안]**
- 높은 타일의 **남쪽(화면 아래) 경계**에 절벽 면을 그린다. 높이 차 1단계마다 절벽 면 한 층. 면 한 층의 높이는 **16px와 32px 두 안을 실험**한다(M17).
- 구현: 절벽 전용 `TileMapLayer`를 바닥 레이어 위에 두고, 각 타일에 대해 `남쪽 이웃의 높이 < 내 높이`이면 이웃 위치에 절벽 면 타일을 놓는다. 높이 차 n이면 n층. 북·동·서 경계는 얇은 턱 타일.
- 편집 시 영향 범위: 바뀐 타일과 그 4방향 이웃(최대 5타일)의 절벽만 재계산한다(전체 재계산 금지).

### 1.5 이동·낙하 규칙 (결정 115·117) — 물리 엔진을 쓰지 않는다 **[제안]**
- 플레이어 이동은 **자체 격자 규칙**으로 검사한다: 목표 타일의 현재 높이(원본 + Δh)와 현재 타일의 차이 d = 목표 − 현재.
  - d ≤ 1(오르기 포함) 이거나 d < 0(내려가기) → 이동 가능(내려가기 d ≤ −2는 낙하, 피해 없음).
  - d ≥ 2(올라가기) → 막힘.
  - 대각선은 인접한 두 직교 타일 모두 통과 가능일 때만 허용.
- 이유: 타일맵 물리 콜리전 갱신 비용을 게이트의 핵심 변수에서 분리한다. 물리 콜리전은 몬스터·대형 단계에서 필요 시 별도 평가한다.
- 갇힘 방지(결정 117 제안): 구덩이 안에서 인접 벽을 깎을 수 있고(흙 +1), 모든 방향이 막히면 안전 복귀 위치로 이동.

### 1.6 건축물 기초 보호 (결정 99) **[제안]**
- 건물 더미는 **평지(주변 높이 동일)** 에서만 배치. 발자국 + 여유 1타일을 **변형 불가 마스크**로 저장(좌표 집합). 마스크 안에서는 쌓기/깎기를 거부하고 임시 표시(오버레이 색)한다.

### 1.7 대형 함정 더미 (결정 74) **[제안]**
- 더미 대형 적(64×64 정도): 고정 경로로 이동. 경로 위 타일의 높이가 **경로 높이 − 1 이하**이면 빠진다 → 무방비 8초 **[가정]** → 탈출.
- AI·전투는 만들지 않는다. 경로 이동과 구덩이 판정만.

### 1.8 델타 저장 (결정 71 분리) **[제안]**
- 파일 형식: 세이브 헤더(`version`, 시드, 월드 크기) + 변경 타일 목록 `(x:int16, y:int16, Δh:int8)`. 이론 하한 5바이트/타일.
- 불러오기: 원본 생성 → 청크 로드 → 델타 적용 → 절벽 재계산.
- **해시 일치 검증:** 저장 전과 불러온 뒤의 (좌표, 높이) 전체 해시 비교.

### 1.9 입력과 프레임 로그
- 입력: 방향키 8방향 이동, 지정 키로 쌓기/깎기(바라보는 방향 1타일), 범위 단계 전환, 마소 구역 선택(디버그 키).
- **로그(CSV):** `engine-gate-plan.md` §3.3 형식. `edit_latency_ms`는 **입력 처리 시작 → 타일·절벽·이동 규칙 갱신 완료** 시점 차이(렌더 완료는 포함되지 않는다는 점을 기록, 화면 반영까지는 사용자가 체감으로 보완). **[측정]**
- 프레임 시간: 게임 루프의 delta와 엔진 성능 모니터(프로세스 시간, 메모리)를 기록. 사용 가능한 모니터 이름은 **[확인]**.

## 4. 구현 시 알려진 위험과 대응

| 위험 | 대응 |
|---|---|
| `set_cell` 단건 호출 비용(포럼 보고) | 청크별 레이어, 일괄 갱신 API가 있으면 사용([확인]), 한 프레임 로드 상한. 비교 측정 |
| 타일셋을 코드로 만드는 것이 오히려 복잡 | 막히면 Pixelorama로 최소 PNG를 만들어 에디터에서 `TileSet` 구성(사용자 작업). 시간 상한 하루 |
| 절벽 오토타일 규칙 복잡도 | 영향 범위 5타일 재계산으로 한정, 전체 재계산을 정답으로 하는 테스트 |
| 높이 값 저장 방식(딕셔너리) 성능 | 변경이 적을 때는 문제 없음. 변경이 수만 단위가 되면 PackedArray로 전환 [측정] |
| 헤드리스에서 측정할 수 없는 항목(프레임, 선명도) | 사용자가 창 모드 실행과 스크린샷 |
| 에디터와 파일 동시 수정 | 수정 단계 동안 에디터는 닫는다 |
| 모델이 기억에 의존한 API 이름 오류 | 2-0에서 검증하고 그 결과로만 구현 |

## 5. 사용자 결정·확인이 필요한 것

## 8. 첫 실측 결과 (Godot 4.7.2, RTX 3060 Ti, 창 모드)
원본: `gate-week2-bench-summary-vsyncon.csv`, `gate-week2-bench-summary-vsyncoff.csv`(vsync 해제). 월드 1024×1024, 청크 32×32. 헤드리스 스모크 행과 30초 Quick 행은 제외하고 아래에 요약.

|---|---|---|---|---|
| vsync 해제, 1080p stream r1, 120초 | 0.368 / 1.389 / 9.99 | 0 | — | 0.082 |
| 1080p stream r2, 120초 | 0.408 / 1.389 / 9.89 | 0 | — | 0.087 |

| 720p stream r2, 120초 | 0.400 / 1.389 / 7.59 | 0 | — | 0.086 |
| 720p edit r2, 120초 | 0.459 / 1.389 / 8.32 | 0 | 0.072 / 0.323 | 0.088 |

| **1080p edit r2, 600초** | 0.490 / 1.389 / 10.76 | 0 | 0.074 / 0.683 | 0.099 |

- 합격선(평균 33ms, p99 50ms, 100ms 초과 0회, 편집 지연 100ms)은 이 PC에서 전부 충족. 10분 실행에서도 100ms 초과 0회, 최대 13.2ms.
- vsync 켠 실행(주사율 120/165Hz 고정)은 프레임 시간이 6.06/8.33ms에 붙어 여유 판단에 쓸 수 없었다. 위 vsync 해제 수치가 실제 작업량에 가깝다.
- 1080p와 720p가 같은 수준: 내부 해상도가 640×360이라 GPU 부하가 작고 CPU(타일·절벽 갱신) 쪽 비용이 지배적임을 시사. (확정은 아님)
- p99 1.389ms가 모든 실행에서 같은 값: 타이머 분해능 때문으로 보이나 확인하지 못함.
- **저사양 외삽 불가:** RTX 3060 Ti 기준 수치다. 통합 그래픽에서의 값은 측정하지 못했다. 평균 0.4~0.5ms가 33ms 합격선의 1.5% 수준이라는 점만 근거로 큰 여유가 있다고 본다.
- **편집 지연**은 타일·절벽 갱신 호출 구간(논리) 값이며 화면 반영까지는 포함하지 않는다.

### 8.1 메모리 증가 — 측정 도구 버퍼로 확인 (2-6c/2-6d)
이전 실측의 메모리 증가(프레임당 약 0.95KB, 10분 1,290MB)는 bench가 프레임 행을 메모리에 쌓은 탓으로 보인다. 행을 디스크로 흘려 쓰도록 바꾼 뒤 1080p stream r2 120초, vsync 해제 재측정:

| | 행 기록 on | 행 기록 off |
|---|---|---|
| 프레임 수 | 387,732 | 411,726 |
| 메모리 시작 → 끝 (MB) | 68.5 → 78.1 | 68.5 → 70.9 |
| mem_mb_max | 75.3 | 70.9 |
| 객체 수 시작 → 끝 | 1743 → 1902 | 1742 → 1901 |
| 리소스 수 / 노드 수 | 6→6 / 31→49 | 6→6 / 31→49 |
| orphan 노드 | 0 | 0 |
| 평균 / p99 / 최대 프레임 (ms) | 0.309 / 0.570 / 10.35 | 0.291 / 0.540 / 4.45 |

- 같은 조건의 이전 120초 실행은 343~380MB였는데 78MB 이하로 내려갔다. 버퍼가 원인이라는 판단과 일치한다.
- 남은 증가: 기록 on +9.6MB, off +2.4MB. 노드 증가(31→49)는 청크 로드에 따른 것으로 보이며 노드·객체 수는 두 경우가 같다. 기록 on 쪽 +9.6MB의 출처는 확인하지 못했다(파일 버퍼 가능성, 미확인).
- 10분 이상 장시간 재측정은 하지 않았다. 메모리 한도(8GB) 판정에는 "게임 본체는 약 70~80MB 수준(이 측정 구간, 월드 로드 반경 2)"까지만 쓰고, 장시간·건물·적이 추가된 상태는 미측정으로 둔다.
- 행 기록이 켜진 실행에서 프레임 최대치가 더 컸다(10.35 vs 4.45ms). 디스크 쓰기 영향일 수 있다(flush 표시 프레임). 앞 절의 최대 프레임 값은 이 영향을 포함할 수 있다.

### 8.2 이 주차에 아직 못 한 것
- 사람이 눈으로 보는 항목: 절벽 가독성(16 vs 32px, M17), 이동 떨림, 2배/3배 확대 선명도, 체커보드 표시.
- 이터레이션 시간(§4.3)과 오토타일 구축 시간(§4.4) 기록.
- 저사양 근사(최소 품질/720p 외 추가 제한) 측정.
- 청크 로드 중 히치의 원인 분리(최대 프레임 시간 7~13ms 구간).
